# 供应链协同需求调研与技术可行性分析

## 0. 文档定位

本篇覆盖需求调研、技术可行性判断，以及最关键的一步——**范围取舍（Scoping）**：为什么最终交付的 v1 用的是 SKU 级公开数据集，而不是最初设想的订单/仓库级企业数据模型。我认为技术判断不是"能不能做"，而是"在当前约束下该做到哪一步、剩下的怎么讲清楚"。

## 1. 项目背景

某制造/快消企业存在多工厂、多仓、多供应商、多承运商协同场景。采购、计划、仓储、销售、物流分别使用独立系统或 Excel 台账，导致订单需求、库存状态、供应商交期、运输节点无法形成统一视图。

本项目要验证的核心问题是："能否用 RAG + 确定性工具路由，把分散的方法论知识和真实运营数据拼接成可解释的策略建议？" 而不是先花大量精力搭一个完整的企业级中台再谈 AI 能力——这是一次刻意的技术路径选择，取舍依据见第 5 节和第 4.2 节。

## 2. 调研对象与高频问题

> 说明：本项目不针对某一具体企业做实地访谈，第 2、3 节的角色画像与痛点归纳自公开的供应链管理行业调研报告与经典文献（引用见第 3.1 节），用于验证"这些问题类型是否真实存在、是否值得用 RAG Agent 覆盖"。

| 角色 | 关注点 | 典型问题 | 依据 |
|---|---|---|---|
| 销售计划 | 客户需求、订单优先级、交付承诺 | 缺少实时库存与产能反馈，预测准确率低 | Gartner 销售运营调研：仅 45% 的销售负责人/销售对本组织的预测准确率有高信心，仅 47% 认为组织数据质量高 [3] |
| 采购 | 供应商交期、价格、MOQ | 供应商状态靠人工确认，信息共享不足 | Deloitte 2025 CPO 调研：64% 的采购官将"提升供应链可见性"列为前三大风险应对策略，61% 将"加强供应商信息共享与协同"列为关键举措——反向说明当前这两项普遍不足 [4] |
| 仓储 | 库存准确率、库龄、周转 | 库存数据延迟，安全库存口径不一 | 行业基准：运营良好的仓库通常以 98%+ 库存准确率为目标，系统更新滞后（system lag）是造成账实不符的常见原因之一 [5] |
| 生产计划 | 排产约束、物料齐套 | 需求变更传递慢，逐级放大（牛鞭效应） | Lee, Padmanabhan & Whang (1997) 对"需求信息逐级传递失真、放大"现象的经典论证 [6] |
| 物流 | 运输节点、异常签收 | 在途状态无法进入计划决策 | MHI & Deloitte《2025 年度报告》：缺乏准确的实时数据是实现端到端供应链协同编排的持续性障碍 [2] |
| 管理层 | 履约率、库存资金、协同效率 | 指标分散，缺少统一看板；风险管理责任分散在多个团队 | McKinsey 全球供应链调研（2023）：仅 8% 的企业认为自己有足够的数字化人才储备，风险管理职责普遍分散在多个团队，44% 报告过重大供应链布局挑战 [1] |

## 3. 关键痛点

| 痛点 | 表现 | 影响 | 依据 |
|---|---|---|---|
| 数据孤岛 | ERP、WMS、TMS、供应商 Excel 独立维护 | 无法形成端到端履约视图 | MHI & Deloitte（2025）：实时数据缺失是端到端供应链编排的持续障碍 [2] |
| 协同效率低 | 需求变更依赖群消息和人工确认 | 响应慢，责任边界不清 | McKinsey（2023）：风险管理责任分散在多个团队 [1]；Deloitte CPO（2025）：61% 的采购官认为供应商信息共享与协同亟待加强 [4] |
| 规则分散 | 安全库存、补货、异常升级规则分布在制度文档和个人经验中 | 新人难接手，策略不可复用 | 经典运营管理文献对标准化操作规程（SOP）价值的论述，参见 `knowledge_base/sop.md` 引用来源 |
| 参数不可追溯 | 服务水平、提前期、MOQ、运输时效未统一沉淀 | 算法与业务口径不一致 | Gartner 销售运营调研：仅 47% 的组织认为自身数据质量高 [3] |
| 异常处理滞后 | 缺货、延期、积压通常在事后暴露 | 影响客户交付和库存成本 | 行业基准：库存系统更新滞后（system lag）导致记录与实物脱节，问题往往在事后才暴露 [5] |

## 4. 需求清单与 v1 范围裁剪

### 4.1 目标需求（North Star，不变）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| R-001 | 建立订单、库存、供应商、物流统一数据模型 | 高 | 能按 SKU/区域/供应商查询统一视图 |
| R-002 | 建立补货与异常预警规则库 | 高 | 输入业务问题可返回规则来源和处理建议 |
| R-003 | 支持需求输入到策略输出自动化 | 高 | Agent 输出建议、风险、动作和依据 |
| R-004 | 标准化数据中台采集、清洗、指标流程 | 中 | 文档中包含数据流、主数据、指标口径 |
| R-005 | 支持 SOP 知识沉淀 | 中 | 知识库可检索缺货、延期、积压处理流程 |

### 4.2 v1 范围裁剪决策

| 需求编号 | v1 状态 | 裁剪依据 |
|---|---|---|
| R-001 | **部分验证** | 可获得的真实公开数据集颗粒度是 SKU 级（产品/供应商/质量/物流），不含 `order_id`/`warehouse_id`；v1 改为验证"SKU + 供应商 + 城市"三维统一视图，订单/仓库颗粒度推迟到 v2 接入企业真实系统后再验证 |
| R-002 | 已验证 | 安全库存/ROP/EOQ/ABC/AQL/供应商评分卡 6 类规则已沉淀进知识库并被 RAG 检索，21 条评测覆盖 |
| R-003 | 已验证 | RAG Agent 端到端准确率 100%（21/21），见 06 |
| R-004 | 已验证（脚本级） | `scripts/clean_data.py` 实现字段映射、四舍五入、同义列一致性校验，详见 05 |
| R-005 | 已验证 | `knowledge_base/` 下 3 篇带引用来源的方法论/SOP 文档 |

这一步是我主动做出的取舍：与其为了"贴合最初的企业级设想"而编造订单/仓库数据（脆弱、不可复现、也无法证明系统真的在处理真实信号），不如换成一个真实、可复现、来源可查的公开数据集，把范围收窄到"SKU 级供应链分析 + 方法论知识检索"，但把每一层都做扎实、做到可验证。R-001 是唯一被裁剪的需求，且裁剪原因是**数据可得性**，不是技术能力不足。

## 5. 技术可行性

### 数据层

v1 使用真实公开数据集（100 行 × 24 列，快消/美妆供应链样本，来源见 `05_数据字典.md`）驱动全部数值类问答；真实落地时可通过 API、数据库同步、消息队列或批量文件接入企业系统，替换 v1 的 CSV 数据源即可，工具层对外接口不需要变。

### 中台层

数据中台负责统一采集、清洗、建模、标签化和指标计算（v1 已用 `clean_data.py` 验证核心清洗规则的可行性，其间发现并处理了一组"同义列名、不同实义、近乎零相关"的真实数据陷阱，见 05）。业务中台负责沉淀补货、供应商协同、异常预警、履约跟踪等可复用能力（v1 已验证"数据查询类"能力；"协同类"能力如替代供应商推荐、自动派单，推迟到 v2，见 03 第 4 节）。

### 智能层

RAG Agent 将业务规则、算法参数、SOP 索引到本地知识库；7 个 MCP 风格工具封装真实数据查询能力；确定性关键词路由判断问题该走知识检索、数据工具、还是两者都要。三层链路已用 21 条真实标注评测集验证，端到端准确率 100%（详见 06）。

### 评测可行性

"能不能落地"不该只看架构图，还要看"能不能被证明是对的"。v1 同步搭建了三支柱评测体系（采样 / 标注 / 指标正交）+ 四层漏斗 bad case 拆解框架，并在评测过程中发现并修正了一次因**标注**（而非模型）导致的召回率虚报（21.4% → 92.9% → 100%），证明了这套评测体系本身能定位问题，而不只是打分。这套方法论已沉淀为可复用 skill `ai-eval-badcase-method`，可以直接迁移到其他 AI 产品的评测搭建上。

## 6. 风险与应对

| 风险 | v1 应对（已发生的真实案例） |
|---|---|
| 数据质量不稳定 | 清洗脚本发现 `lead_times_days` 与 `lead_time_days` 看似同义、实则近乎零相关（r≈-0.003），用"先断言一致性，不一致就报错"替代"静默合并"，避免脏数据静默进入工具层 |
| 业务规则频繁变化 | 规则以带引用来源的 Markdown 沉淀，版本变化只需替换 `knowledge_base` 文件，RAG 自动生效，无需改代码 |
| 评测/标注本身出错，而非模型出错 | 曾因 chunker 切片位置编号与人工 gold 标注对不上，导致 Recall 虚报 21.4%；改用"语义锚点（来源文件 > 标题）"替代"位置编号"后修复，见 06 |
| Agent 输出不可解释 | 输出统一包含 scenario/findings/strategy/risks/evidence 五段结构，并标注 RAG 命中片段的来源和相关度分数 |
| 与真实系统集成成本高 | v1 用本地 CSV 原型验证全部链路后再谈接入，避免"先接系统再发现方法论跑不通"的返工 |

## 7. 结论与实施路线图

v1 已完成技术可行性验证：本地真实数据集 + 规则知识库 + 确定性路由 RAG Agent，端到端可运行、可评测、可解释。

| 阶段 | 目标 | 关键交付 | 状态 |
|---|---|---|---|
| V1（已完成） | 验证 RAG + 工具 + 路由架构在真实 SKU 级数据上可行 | 7 个真实数据工具 + 3 篇带引用来源的知识库 + 21 条评测，e2e 100% | 已完成 |
| V2（规划） | 接入企业真实订单/仓库系统，补齐 R-001 剩余颗粒度 | 订单/仓库实体建模，补货策略服务（安全库存/ROP 自动触发），见 03 第 3、4 节的差距表 | 待启动，需企业数据接入 |
| V3（规划） | 沉淀中台能力，扩展到更多供应链协同场景 | 供应商替代推荐、自动化协同工作流、统一看板 | 待 V2 验证后规划 |
