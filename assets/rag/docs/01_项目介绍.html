项目介绍

项目名称

供应链协同中台与 MCP-RAG Agent

项目定位

一个面向制造/快消供应链场景的端到端 AI 产品原型。我独立完成从需求调研、技术可行性分析、架构设计、Agent 原型开发到评测体系搭建的全流程。用于验证如何把一个模糊的业务诉求，拆解成可复用的知识、可验证的数据、可解释的决策路径，并如实地说明它的边界。

我解决的问题（以及我如何验证它是真问题）

供应链协同场景里，业务人员长期面临两类割裂：

  1. "怎么算"割裂——安全库存、再订货点、EOQ、ABC 分类、供应商评分卡这些方法论散落在制度文档和老员工经验里，新人难以复用，口径也不统一。
  2. "数据在哪"割裂——真实的库存水平、缺陷率、供应商交期分布在系统或表格里，业务人员想知道"这个 SKU 该不该补货"，得自己跑数、自己套公式，还容易套错或套错版本的公式。

调研阶段我梳理了销售计划、采购、仓储、生产计划、物流、管理层六类角色的高频问题（详见 02_需求调研与技术可行性分析.md），确认这两类割裂是可复现的真实场景，而不是"为了展示 AI 能力而想象出来的应用场景"。

我的方案：把"怎么算"和"数据在哪"拆成两条独立可验证的链路

  • RAG 管知识：把安全库存 / ROP / EOQ / ABC / AQL / 供应商评分卡等方法论，连同引用来源（Chopra & Meindl《供应链管理》、Heizer《运营管理》、ANSI/ASQ Z1.4、APICS Dictionary）沉淀成本地知识库，按标题切片并携带来源路径检索。
  • MCP 工具管数据：把真实数据集查询封装成 7 个结构化工具（查 SKU、查低库存、供应商缺陷率排名、分城市平均提前期、ABC 分类、供应商评分卡等），保证"数值类回答"永远来自真实数据行，不靠模型生成或臆测。
  • 确定性意图路由：用可解释的关键词规则判断一个问题该走知识检索、数据工具，还是两者都要（hybrid），而不是默认上 LLM 路由——这个选择本身也是一次有评测数据支撑的技术取舍（详见 04_RAG_Agent_设计说明.md 第 8 节）。

技术实现（v1 范围，真实可运行）

  • 数据：真实公开供应链数据集（100 行 × 24 列，快消/美妆行业样本），来源见 05_数据字典.md。
  • 检索：Markdown 按标题切片 + TF-IDF 关键词检索，零外部依赖。
  • 工具层：Python 实现 7 个真实数据工具 + MCP 风格 JSON-RPC 服务（tools/list + tools/call）。
  • 评测：21 条人工标注评测集，覆盖 rag / tool / hybrid 三类问法，配独立参考实现防止"自己证明自己对"。

项目结果

指标 结果 说明
端到端准确率 end2end_accuracy 100%（21/21） 修复标注错位与工具派发缺陷后的真实结果
召回率 Recall@3 100%（14/14） 21.4%，定位到根因是标注错位而非检索器问题
意图路由准确率 intent_accuracy 90.5%（19/21） 保留 2 条边界 case

两条未命中的 case 端到端答案依然正确，说明这是"路由标签与人工标注存在边界分歧"，而不是系统缺陷。完整拆解过程见 06_RAG_Agent评测与BadCase复盘.md。

总结

将整个项目拆解成"可复用的知识 + 可验证的数据 + 可解释的决策路径"；并在指标和常识出现矛盾时（比如召回率一度只有 21.4%），我选择依据四层漏斗（现象/假设/验证/归类）对Bad Case进行拆解寻找问题根本，而不是急着换更贵的模型——这次怀疑最后证明是对的：根因在标注错位，不在模型能力。
