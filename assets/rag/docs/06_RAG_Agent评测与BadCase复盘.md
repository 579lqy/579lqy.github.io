# RAG Agent 评测与 Bad Case 复盘

> 配套代码：`supply-chain-rag-portfolio`（零外部依赖，21 条评测集可复跑）

## 0. 与其他文档的关系

`02_需求调研与技术可行性分析.md` 交代了这个项目为什么要做、v1 范围怎么定；`03_数据中台与业务中台流程框架.md` 交代了数据和能力怎么分层；`04_RAG_Agent_设计说明.md` 交代了 Agent 内部架构怎么设计。本文档是这三篇的"验证环节"：架构设计得再合理，也要靠一套评测体系把它证明出来——这篇复盘记录的就是这套评测体系怎么搭、搭出来之后发现了什么问题、怎么修的。

## 0.1 背景与一句话结论

我做了一个供应链协同 RAG Agent：真实公开数据集（100 行 × 24 列）→ 清洗 → MCP 风格工具层（查实时数值）+ 本地知识库 RAG（查 SOP/公式）+ 确定性意图路由（`rag/tool/hybrid`）。

最初我自己跑出的评测报告写着 **Recall@3 = 94.7%（接近完美）**。但我没有信这个数字——因为我用同一句 query 去实时检索，黄金 chunk 明明排第 1，eval 却判它 miss。顺着这个矛盾追下去，发现**那 94.7% 是假象**，根因在标注，不在模型。

最终结论：
- **端到端准确率 100%（21/21）**
- **召回率 Recall@3 100%（14/14）**
- **意图路由准确率 90.5%（19/21，仅 2 条边界 case）**

这篇复盘是**如何建立一个你敢信的评测体系，以及当它报红时，怎样用四层漏斗拆解根因**。

---

## 1. 为什么需要评测体系：从第一性原理出发

RAG Agent 是「检索 + 工具 + 路由 + 生成」的拼接体。任何一个环节出问题，最终用户看到的都是「答非所问」。如果只盯一个总分（比如「回答正确率 94.7%」），你根本不知道：

- 是检索器没召回？还是路由判错了意图？还是工具抽错了参数？还是**标注本身标错了**？
- 改了一处，另外几处的真实水位变了吗？
- 分数涨了，是真的变好了，还是评测集被「刷」过了？

所以评测体系的设计目标不是「跑出高分」，而是**能定位问题、且指标之间互不替代**。我把它拆成三支柱。

### 1.1 三支柱

| 支柱 | 回答的问题 | 在本项目落地 |
|------|------------|--------------|
| **采样 Sampling** | 测的是「会的部分」还是「全貌」？ | 21 条覆盖 `rag(6)/tool(7)/hybrid(8)`，刻意包含纯知识、纯数值、公式+数据三类 |
| **标注 Labeling** | gold（标准答案）可信吗？ | gold 用「`source > 第N节标题`」语义锚点解析，**不依赖**脆弱的位置编号 |
| **指标正交 Orthogonal** | 一个分能代替所有分吗？ | Recall 只测检索器；e2e 测全链路；intent 测路由——三者独立，不能互相掩盖 |

三支柱的优先级是 **标注 ≥ 采样 ≥ 指标**。没有可信的标注，后面全是空中楼阁——这一点在第 3 节会被血淋淋地验证。

### 1.2 四层漏斗（Bad Case 拆解框架）

每个红色 case 都按这四层走，且**必须一层一层来，不能跳**：

```
现象层  ── 它报错了 / 答错了（只看表面）
  ↓
假设层  ── 至少列 2 个候选根因（检索？工具？路由？生成？标注？）
  ↓
验证层  ── 跑真实中间产物，控制变量，证伪/证实假设
  ↓
归类层  ── 落到根因树的一个叶子（检索/工具/路由/生成/标注）
```

**在验证层跑出真凭实据之前，不许改代码。** 否则你改的往往是你「觉得」的原因，不是真原因。

### 1.3 独立参考实现（防循环论证）

评测对 `tool/hybrid` 的答案，用的是**和 Agent 内部不同代码路径**的参考值（独立 `groupby`、独立排序、独立公式代入），再比对。如果评测直接复用 Agent 自己的函数结果，那叫「自己证明自己对」，没有任何意义。

## 2. 第一轮复盘：标注错位

### 2.1 现象

`eval_results.json` 报：**Recall@3 = 21.4%（rag+hybrid 子集里只有 3/14 命中）**。

但同一时刻，我手动用 `LocalRetriever.search("再订货点 ROP 的公式是什么？")` 看 top3，黄金 chunk `business_rules.md / 2. 再订货点` **排第 1**。检索器好好的，eval 却说没召回。矛盾。

### 2.2 假设（列了两个）

- H1：检索器真烂，召回能力不足 → 该升级向量混合检索 + rerank。
- H2：标注（GOLD）写错了，eval 判分逻辑和检索器的 chunk 编号对不上。

### 2.3 验证（控制变量）

我去翻 eval 的 GOLD 定义：原实现把「第 N 节」硬编码成 `id = source + "-" + (-N)`。但 chunker 的实际规则是——**H1 标题加前言被切成第 1 块（id `-1`），之后的每个 `##` 顺序编号从 2 开始**。也就是说，eval 认为「第 2 节 = id `-2`」，但真实 chunker 给的是 `-3`。**GOLD 整体错开了一位**。

一个最小验证：拿 RAG-02 的 query 打印真实召回列表，`-3` 赫然在 top3；eval 却拿 `-2` 去比对 → miss。H2 证实，H1 证伪。

### 2.4 修复：语义锚点取代位置编号

gold 不再靠「第几节」，而是从 `case["grounding"]`（如 `"business_rules.md > 2. 再订货点"`）按标题语义解析：

```python
def resolve_gold(case, docs):
    g = case.get("grounding")
    src, _, sec = g.partition(" > ")
    for d in docs:
        if d["source"] == src and (d["title"].startswith(sec) or sec in d["title"]):
            return d["id"]
    return None
```

同时把 21 条 grounding 归一化为纯净的 `source > 第N节标题`（清掉旧版带 `clean_supply_chain.csv` 脏后缀、个别缺 `>` 的问题）。

### 2.5 真实基线

| 指标 | 值 | 说明 |
|------|-----|------|
| 意图路由 intent | 90.5%（19/21） | 真实 |
| 召回率 Recall@3 | **92.9%（13/14）** | 唯一 genuine 缺口是 HY-05 |
| 端到端 e2e | 85.7%（18/21） | 5 个 flagged case |

**关键认知转折**：召回的真实水位是 92.9%，不是 21.4%。TF-IDF 关键词检索器对这种「公式/SOP 知识问法」其实够用。**盲目升级向量检索 + rerank 是错的**——那是在为假问题买单。真正要修的是：工具派发措辞/覆盖 + 路由边界 + 1 个 gold 误标。

## 3. 第二轮复盘：5 个 Genuine 失败点的拆解与落地

修复标注后，仍有 5 个 flagged case。我逐个走四层漏斗。

### 3.1 TOOL-02：「最低的 5」为什么只回了 3 条

**现象**：query =「列出 Mumbai 库存水平最低的 5 个 SKU」，工具返回 3 条，e2e 失败。

我（引导用户）的第一反应是：「是不是意图识别把纯知识误判了？或者是分词问题？」——这是很多人的本能假设。验证层立刻把它证伪：

```python
route("列出 Mumbai 库存水平最低的 5 个 SKU")  # -> 'tool' ✅ 路由没问题
"最低 5" in q                                # -> False ❌ 真根因在这
```

根因不在路由、不在分词，而在**工具派发器的字符串匹配**：原代码写死 `"最低 5" in q`，但真实 query 是「最低的 5」——中间多了个助词「的」，匹配失败，于是 `top_n` 落回默认 3。

**修复**：用正则容忍「的」这类穿插汉字：

```python
m = re.search(r"最低\D*(\d+)", q)   # \D* 吃掉"的"以及任何非数字
top_n = int(m.group(1)) if m else 3
```

> 元认知点：① 漏斗必须**顺流追踪 + 控制变量**，eval 里 `intent_ok=True` 已经证明路由无责，根因一定在更下游；② 检索器的 tokenizer 只服务召回，派发器是字符串/正则匹配，**二者不可混淆**；③ **沉默失败比响亮失败更危险**——返回 3 条「看起来正常」，比返回空「乍一看就错了」更难被发现，这正是评测存在的意义。

### 3.2 TOOL-05：「低于 10」抽到了数却没派发

**现象**：query =「库存水平低于 10 的 SKU 有哪些？」，派发返回 `{}`，e2e 失败。

**假设**：又是分词/意图问题？（惯性思维）

**验证**：参数抽取层 `_extract_threshold` 实打实抽到了 `10`，证明抽取没问题；问题在**抽取层和派发层失同步**——dispatch 里没有「库存 + 低于 + 阈值」这个分支，抽到的 10 无人消费，落入兜底 `{}`。归类为**工具派发根因（分支缺失）**。

**修复**：补一个分支消费已抽到的阈值：

```python
if "库存" in q and thr is not None:
    return {"tool": "low_stock_skus",
            "result": low_stock_skus(location=loc, threshold=thr)}
```

### 3.3 HY-05：检索缺口 + gold 误标，双重根因

**现象**：「Mumbai 仓哪个 SKU 最该优先补货（结合库存覆盖与缺陷风险）？」e2e 失败，且 sop 块召回排第 10。

**拆解**：
1. **gold 误标**：原 grounding 锚到 `SOP-2 供应商评分卡`，但 query 问的是「缺陷风险」，真实依据应是 `SOP-1 缺陷率判定`（它本身排第 1、强召回）。这是标注错误，修正 grounding 后检索缺口消失。
2. **派发缺失**：即便检索对了，原 dispatch 也没有「优先补货」分支。补一个综合「库存最低 + 缺陷率最高」的派发分支。
3. **轻量补检索**：给 `LocalRetriever` 加 `QUERY_SYNONYMS`（`补货→评分卡/风险`、`风险→缺陷率`），只针对确为知识块真实关键词的问法扩展，**不是盲目上 embedding 检索**。

> 这是本轮唯一一个「真·检索缺口」，而且根因一半在标注、一半在派发。再一次印证：先修标注和分工，再谈检索升级。

### 3.4 TOOL-01 / HY-08：路由边界，归类而非缺陷

这两条 e2e 都**答对了**，只是路由标签和评测集标注有分歧：
- **TOOL-01**「SKU0 缺陷率是否超 AQL」：标注 `tool`，路由判 `hybrid`（问法同时含公式词 AQL + 数据实体 SKU0）。
- **HY-08**「C 类 SKU 补货管控」：标注 `hybrid`，路由判 `rag`（「C 类」未被路由词表识别为具体数据实体）。

归类为**意图边界 / 标注边界**，纯 intent 指标问题，系统功能无 bug。我选择把它们作为**诚实展示**保留下来（见第 4 节），而不是偷偷把标注改掉刷分。

### 3.5 落地后的真实指标

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 端到端 e2e | 85.7% | **100%（21/21）** |
| 召回率 Recall@3 | 92.9% | **100%（14/14）** |
| 意图路由 intent | 90.5% | **90.5%（19/21）** |

> 注意：召回从 92.9% → 100% 的提升，主要来自修正 HY-05 的 **gold 误标** 和补派发，**不是换检索器**。这和第 2 节的判断一致。

## 4. 最终结果与边界（诚实展示）

```
端到端 end2end_accuracy   = 100.0%  (21/21)
召回率 recall_at_3        = 100.0%  (14/14)
意图路由 intent_accuracy  =  90.5%  (19/21)
需复盘（仅意图边界）      : ['TOOL-01', 'HY-08']
```

- **两指标 100% **：标注用了语义锚点、评测用了独立参考实现、指标彼此正交。
- **intent 90.5% 是诚实的**：TOOL-01 / HY-08 是意图/标注边界 case，端到端答案均正确。要推到 100%，只需在 `intent_router.py` 加两条词表映射（HY-08 补 `[ABC]类→abc`，TOOL-01 改标 hybrid），但当前选择保留为「评测边界 vs 业务正确」的例证实证。
- **绝不为了一个数字好看去动 gold**：这是整个复盘的底线。

## 5. 方法论沉淀（可复用）

这套方法已固化为可迁移 skill `ai-eval-badcase-method`，适用于任何 AI 产品（对话 / 推荐 / Agent / RAG）：

1. **标注优先原则**：指标可信度 ≤ 标注可信度。gold 用语义锚点，不用位置编号。
2. **四层漏斗纪律**：现象 → ≥2 假设 → 验证（跑真实中间产物）→ 归类。验证前不改码。
3. **指标正交**：召回 / e2e / 路由 各管一段，互不替代，避免单一总分掩盖问题。
4. **独立参考实现**：评测答案用与系统不同的代码路径算，防循环论证。
5. **控制变量 + 顺流追踪**：eval 已证明上游无责，就别在下游瞎改；检索器 tokenizer 与派发器匹配是两回事。
6. **中文正则坑**：派发用 `最低\D*(\d+)` 容忍「的」等穿插，避免写死字符串漏匹配。
7. **数据先校验再合并**：`lead_times_days` 与 `lead_time_days` 看似重复，实则近乎零相关（r≈-0.003），必须分别保留——先断言一致性，再合并，绝不静默合并。
8. **不被假基线驱动**：当指标和常识矛盾，先怀疑评测，再怀疑模型；避免为虚构问题做无效工程（如盲目上向量检索）。
