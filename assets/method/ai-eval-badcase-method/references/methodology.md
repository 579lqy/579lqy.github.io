# AI 评测体系与 Bad Case 拆解 · 完整方法论与真实案例

> 配套 skill `ai-eval-badcase-method`。本文档给 SKILL.md 补上推导链、可复现的真实案例、与陷阱目录。

***

## 一、第一性原理：为什么必须有"评测体系"

**AI 系统 vs 传统软件的本质差异**决定了评测不是可选项，而是唯一能证明"它能用"的手段：

- 传统软件：`if A then B`，输出可枚举、可穷举单测；
- AI 系统：输出**概率性、不可枚举**（同一 prompt 可能变、没见过的问法会崩）。

**推论**：永远无法靠"代码写对了"证明"系统答得对"，只能靠**在代表性样本上的客观测量**去*推断*整体能力（统计推断思想：样本烂必然整体烂，样本好才能说大概率好）。

所以一个评测体系 = **采样 + 标注 + 指标**三件套。缺任一都会翻车：

- 不抽样 → 指标虚高；
- 不标注 → 无法判定对错；
- 指标不分解 → 不知道坏在哪。

```
AI 输出概率性、不可枚举
        │
        ▼
必须用"代表性样本上的客观测量"推断整体能力（统计推断）
        │
        ▼
评测体系 = 采样(评什么) + 标注(怎么判) + 指标(报什么·正交分解)
        │
        ├─ 采样错 → 指标虚高（只放简单题 Recall 必虚高）
        ├─ 标注错 → 整个 bad case 归因是空中楼阁（最致命）
        └─ 指标混报 → 不知道坏在检索还是工具
```

***

## 二、三支柱详解（可迁移到任何 AI 产品）

### ① 采样 = 定义"系统真实会被怎么用"

- 先枚举用户意图/查询类型分布（例：rag 知识问答 / tool 数值 / hybrid 公式套真实数据）；
- 按分布**分层抽样**构造用例，必须含 happy / edge / adversarial 三类；
- hybrid 占比应与其差异化价值匹配（它才是 Agent 真正的壁垒，不能当少数）。

### ② 标注 = ground truth 的权威来源

- rag：标 `gold chunk id`（检索是否命中正确块）；
- tool：**用独立参考实现算数值当标准**（绝不能用系统自己输出当标准，否则循环论证）；
- hybrid：公式 + 数值都正确；
- 再配 `rubric`（判定细则，如"数值误差<1% 算对"）。

### ③ 指标 = 每个指标测不同东西，必须正交分解

- `Recall@K` → 只测**检索器**（只看 rag+hybrid 子集）；
- `端到端准确率` → 测**整体**能否答对用户（全部用例）；
- `意图准确率` → 测**路由**分类对不对（独立维度）。
- **绝不混报**：混在一起，永远不知道坏在检索还是工具。

## 三、四层漏斗（Bad Case 拆解固定流程）

```
现象层 → 假设层 → 验证层 → 归类层
   │         │         │         │
   │         │         │         └ 落到根因树(检索/工具/路由/生成/标注)
   │         │         └ 跑真实中间产物证伪，不靠直觉
   │         └ ≥2 候选根因，皆当假设非结论
   └ 打开结果文件，看 recall/e2e/intent 三列，定位哪根线挂了
```

### 每层操作动作（以真实案例示范）

- **现象层**：打开 `eval_results.json`，看 `recall3 / e2e / intent_ok` 三列，先定位"哪根线挂了"。如 RAG-02：`recall3=✗`、`e2e=✗`、`gold=business_rules.md-2` 且 top3 无 `-2` → 现象=**检索未命中正确块**。
- **假设层**：至少列 **2 个候选根因**，绝不急于定论。
- **验证层**：跑 `LocalRetriever.score(query, chunk)` 看 `-2` 真实打分、看 chunker 输出确认切片是否完整——**用中间产物证伪，不靠直觉**。
- **归类层**：把验证结论落到根因树某一类，写进迭代 backlog。

### 归因的"控制变量"威力（以 HY-05 为例）

它 `recall3=✓`（检索对了）却 `e2e=✗` → 检索层输出是对的，根因必在检索层**之后**（工具算数 / 生成格式 / 标注口径）。一步就排除了"检索"这个最大嫌疑，不用猜。

***

## 四、根因分类树

按系统模块切，最稳：

- **检索根因**：检索器没把正确块送进来（召回低 / 切片错 / 嵌入差）
- **工具根因**：数值算错 / 字段取错 / 返回条数或口径偏差
- **路由根因**：意图分类误判，派发错了模块
- **生成根因**：检索和工具都对，但 LLM 拼答案/prompt/格式错了
- **标注根因**：gold 本身口径有歧义（最容易漏，却会冤枉系统）

## 五、真实案例库（来自供应链 RAG Agent 评测实战）

### 案例 A · 标注错位制造假指标

**背景**：21 条评测初跑，Recall\@3 报 **21.4%**，于是推断"TF-IDF 单字中文切分太弱，必须升级向量混合检索+rerank"。

**验证层翻盘**：

- 实时跑 `LocalRetriever.search("再订货点 ROP 的公式是什么？")`，gold chunk 的真实分数排第 1（31.66），明明进了 top3；
- 但 `eval_results.json` 却写它 `recall3=false`、top3 是别的块——两个证据源对不上。
- 控制变量排查：读 `chunker.py` 发现它把 H1+前言切成 `business_rules.md-1`，于是"1. 安全库存"实际是 `-2`、"2. 再订货点"实际是 `-3`……而 `eval_rag.py` 的 GOLD 映射**按"第 N 节=-N"写死**，整体错开一位；hybrid 的 grounding 还带 `+ ...` 脏后缀、个别缺 `>`。
- 用"按 grounding 语义锚点解析"替代脆弱编号、归一化 grounding 后重跑：**真实 Recall\@3 = 92.9%（13/14）**，端到端 85.7%，意图 90.5%。

**结论 / 可迁移教训**：

- 一个指标的可信度 ≤ 它标注的可信度。**标注错位能让整个评测翻盘**。
- 若当时没做验证层，直接照 21.4% 去"升级向量检索"，代价有三：① 92.9% 的检索器被改出 embedding/rerank 新 bug，召回反降；② 真问题（工具派发 bug）一直没动，e2e 原地不动。
- **修复模式**：gold 从"脆弱的位置编号"改为"按 grounding 语义锚点解析"（不依赖编号偏移），并在评测脚本里断言"每个 gold 都能在 chunks 里解析到"。

### 案例 B · 工具派发 bug（沉默失败）

**TOOL-02**：query=`Mumbai 库存最低的 5 个 SKU 是哪些？` → 派发 `low_stock_skus(top_n=3)`，**只回 3 条，标准是 5 条**。

- 现象层：intent\_ok=True（路由没问题），e2e=✗。
- 假设层：①意图错？②路由纯问答不调工具？③"的"把"最低5"拆开 → 进了 top\_n=3 分支？
- 验证层：跑 `route(q)`='tool'（假设①②错）；`'最低 5' in q = False`（中间隔着"的"），实际 top\_n=3（假设③对）。
- 归类层：**工具派发根因 / 派发参数错配**——硬写字符串 `"最低 5"` 不匹配带"的"的自然语言。

**TOOL-05**：query=`哪些 SKU 的库存低于 10？` → 派发返回 `{}`（空）。

- 验证层：`_extract_threshold` **其实抽到了 10**，但 `dispatch_tool` 里既没有"库存+低于+阈值"的分支，也没把 `threshold` 传进 `low_stock_skus(threshold=...)` → 落入兜底空。
- 归类层：**工具派发根因 / 派发分支缺失**（抽取层与派发层失同步）。

**元认知（易错配）**：常有人把"返回条数不对"误归到"意图/路由/分词"，但 `intent_ok` 早提示路由没问题，且派发器用的是**原始字符串** **`in`** **匹配**，根本没调 tokenizer。"分词"服务于**检索器**，派发器是**字符串/正则匹配**。

**沉默失败警告**：TOOL-02 返回 3 条 SKU 看起来完全正常，肉眼测代码永远发现不了，只有独立参考实现能发现。

## 六、陷阱目录（pitfall catalog）

| 陷阱           | 表现                          | 后果                | 防御                   |
| ------------ | --------------------------- | ----------------- | -------------------- |
| **标注错位**     | gold 用脆弱编号/脏格式，与真实 chunk 偏移 | 整个评测翻盘（Recall 假低） | gold 用语义锚点解析 + 断言可解析 |
| **循环论证**     | 用系统自身输出当 ground truth       | 指标永远 100%，毫无意义    | tool/numeric 用独立参考实现 |
| **样本失真**     | 评测题与知识出自同一份手写材料             | Recall 虚高（自证预言）   | 换真实/公开数据，或标注"示例性"    |
| **指标混报**     | Recall/端到端/意图混成一个数          | 不知坏在哪             | 正交分解，各测各的子系统         |
| **沉默失败**     | 返回"少几条/空"但不报错               | 肉眼发现不了            | 独立参考实现逐条比对           |
| **抽取-派发失同步** | 阈值抽到了但无人消费                  | 落入兜底空             | 派发层显式消费抽取结果          |
| **跳层定结论**    | 看到现象直接改代码                   | 修错地方、埋新 bug       | 强制四层漏斗，验证层用证据        |
| **基于假基线迭代**  | 先改代码再验测量                    | 白费工程              | 任何修复前先重验测量本身         |
